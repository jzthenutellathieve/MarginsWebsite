## API and privacy boundaries

All actions use `/api/community?action=…`. Mutations require JSON and the production website Origin. Cross-site mutations and preview writes are refused. Access and refresh tokens are in `__Host-` cookies marked `HttpOnly`, `Secure`, `SameSite=Lax`; responses are private and not cached. Supabase validates the user behind a session. Tokens, user email addresses and provider error details are not returned in community responses.

- Public reads: `status`, `feed`, and `note&id=…` for an approved static or member note.
- Account reads: `session`, `mine`; `review` is owner-only and contains notes and comments. Following the owner's October 7 request, every verified account is a member. Session and verification return `membership: 'approved'` and `isMember: true` for verified users, plus `avatar` (a signed photo URL or `null`). These fields do not grant editorial privileges. Joining and login share one entry; there is no separate membership application.
- Auth writes: `request-code {email}`, `verify {email,token,name?}`, `logout {}`. Unsupported addresses receive a generic response to avoid account enumeration. Provider throttling returns an honest 429 retry error. The code screen displays the requested address above the code field, identifies the sender, and offers Resend code after a 60-second cooldown. Browser calls use `/api/community/` to avoid an extra trailing-slash redirect.
- Profile writes: `profile {name,avatar?}` requires a verified session and can edit only that account. Omit `avatar` to keep the current photo, send `null` to remove it, or `{base64,mime}` to upload a new JPEG, PNG or WebP photo up to 2 MiB. The server validates image signatures and dimensions and chooses the path. Caller-supplied paths, account IDs and roles are rejected. A database row lock serializes replacements; old photos are deleted after the update. Avatars appear in the owner's account area; they do not claim a static member card or create an unreviewed public profile.
- The old `request-membership` API and membership moderation actions are retired. The original membership table and service-only SQL functions are retained for history but are not used to grant account or posting access; do not rerun the baseline or delete them as part of this UI change. The curated public member directory remains separate from authenticated accounts.
- Interaction writes: `like {id,liked}`, `comment {id,text}`, `view {id,eventId}`. Views count page-view events, not unique people. Retries reuse the same UUID and are deduplicated for 24 hours; totals persist independently of receipts.
- Any verified reader account may upload images, submit Notes, like or comment. Notes and comments still await editor approval. The account page shows the note composer directly after login, with links to submissions and profile editing. Full articles are sent to `xingtong.themargins@gmail.com` for editorial consideration; this feature does not add an article CMS.
- `upload {base64,mime}` accepts JPEG, PNG or WebP up to 2 MiB decoded, with matching signatures and bounded image dimensions. It returns a private, account-owned path, not a public URL.
- `submit {title,text,date,media:[{path,alt}],permission:true}` allows titles up to 120 characters, text up to 4,000, and 0–4 photos. Text is required when there are no photos. The server owns author identity and publication status. Only the uploader's unused paths can be attached. Submitted notes and comments remain pending until approved.
- `moderate {kind:'note'|'comment',id,approve}` requires the verified owner and changes publication visibility atomically. Member signup never grants this permission.

Content is plain text, including titles, display names, image descriptions and comments. The client must render it with `textContent`, never `innerHTML`. Chosen names are display labels, not proof of identity or links to the existing static member list.

Private note uploads are signed only when an approved note is read, or its owner/editor views the submission. Profile photos are signed only in their owner's session/profile response. Signed links last one hour; reload the feed or account page if an old photo link expires. Existing issued links can remain valid until expiry after a post is rejected; they are not permanent public bucket URLs. Rejected or unattached uploads are not publicly listed. Establish an administrative retention policy for abandoned uploads, superseded avatars whose cleanup failed, and old rate-limit rows before sustained public use. If a profile RPC response is lost, the new object is retained because the update may already have committed; retention must check stored profile references before deleting objects.

Rate limits are shared in Postgres across server instances. Likes use a unique account/note key and an atomic desired-state RPC. View deduplication, media ownership/claiming and moderation also use transactions. All community tables use RLS with access revoked from browser database roles; only server service-role requests can access them. Storage is private with restrictive policies guarding against broad policies on unrelated buckets.
